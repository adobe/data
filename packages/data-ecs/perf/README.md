Generated by `pnpm perf:report` from `history/`; don't edit it by hand.

- `pnpm perf [filter]` runs the node benchmarks, bundled as in production, and compares each with this machine's last record. `pnpm perf:browser` runs the chromium ones: main thread, workers and GPU.
- Add `--record` to append the results to `history/<machine>.jsonl` and regenerate this file. Record on an idle machine, and commit the record with the change it measures.
- **ns per N** is the fastest run's time divided by N. **Best** is the time to move the fewest bytes an ideal implementation must, in this ECS's storage model, at the fastest copy bandwidth the run measured, with data in the caches; **× best** is how far from it the run is, and **Room** the milliseconds between them. **Change** compares with the previous record on the same machine; beyond ±10% it says slower or faster.

## Benchmarks

### create

Spawning entities of six components, two of them tags, over four archetypes, through a main-thread system and the sync point that applies them: loading a level, a burst of particles.

- **N:** 1M spawns; usually 100–100K.
- **Best:** 48 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each entity writes its 32 bytes of values, its 8-byte entity and its 8-byte location.

### create flat

The same spawns with eight scalar components each, values passed inline.

- **N:** 1M spawns; usually 100–100K.
- **Best:** 48 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each entity writes its 32 bytes of values, its 8-byte entity and its 8-byte location.

### create flat dynamic

The same spawns from value objects built first, as spawns from data or from another system's results are.

- **N:** 1M spawns; usually 100–100K.
- **Best:** 48 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each entity writes its 32 bytes of values, its 8-byte entity and its 8-byte location.

### move

A kernel adding a vec3 to another for the rows with two tags: integration, animation, any per-row update.

- **N:** 250K matched rows; usually 1K–1M.
- **Best:** 36 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each row reads 12 bytes of velocity and reads and writes 12 bytes of position.

### churn

A main-thread system despawning a tenth of its rows and spawning as many: projectiles, particles, pooled UI.

- **N:** 1M rows visited; usually 1K–100K.
- **Best:** 29 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each row reads 16 bytes; each tenth swaps the last row into its hole, 88 bytes, and spawns one of 44.

### retag

A main-thread system adding a tag to a tenth of its rows and removing it from another tenth: state flags such as selected or visible that move entities between archetypes.

- **N:** 1M rows visited; usually 1K–100K.
- **Best:** 39 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each row reads 4 bytes; each fifth moves, copying its 44 bytes and swapping the last row into its hole.

### sparse changed

A kernel filtered on `changed` after 1% of rows changed, scattered: reacting to edits, such as recomputing bounds of what moved.

- **N:** 1M rows in the archetype; usually 10K–1M.
- **Best:** 8.24 bytes per N at the copy bandwidth of one thread, the fastest it measured. Every chunk has a change, so each row's 8-byte tick is read; the changed 1% read 12 bytes and write 12.

### sparse changed clustered

The same with the 1% in one contiguous run of rows, as edits to recently spawned entities are.

- **N:** 1M rows in the archetype; usually 10K–1M.
- **Best:** 0.33 bytes per N at the copy bandwidth of one thread, the fastest it measured. Chunk ticks are scanned; the changed 1% read their 8-byte ticks and 24 bytes of values.

### log rebuild 100K

A joined thread rebuilding its object columns over 100K rows from the layout directory, as when it fell further behind than its log holds.

- **N:** 100K rows; usually 1K–100K.
- **Best:** 60 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each row reads its 8-byte entity, 4-byte tag and 16 bytes of ticks, and writes its entity, object and ticks.

### handoff

Ticks of ten tiers alternating the world's thread and a joined worker, empty systems: five tasks posted and waited for each tick, as when systems that write a worker's objects sit between the world's.

- **N:** 1K ticks; usually 1–1.
- **Best:** 1,280 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each of five handoffs moves at least the task's posted, done, payload and completion lines between cores.

### fused tiers

Ticks of ten consecutive tiers on a joined worker, empty systems, which run as one task: a worker filling objects whose systems follow one another.

- **N:** 1K ticks; usually 1–1.
- **Best:** 256 bytes per N at the copy bandwidth of one thread, the fastest it measured. One task moves at least its posted, done, payload and completion lines between cores.

### despawn objects 10K

A sync point despawning 10K entities whose objects a joined worker fills, with a finalizer there reading the object and a vec3: releasing DOM nodes or GPU handles, which the world's thread doesn't wait for.

- **N:** 10K despawns; usually 1–10K.
- **Best:** 56 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each despawn frees its 8-byte location and entity, and writes its stop: its entity, archetype, row and tag, 20 bytes, and its 12-byte vec3, read and written.

### tail prompt

Ticks of a world system and a terminal system on a joined worker over 1,000 rows, which runs after the sync point and finishes before the next tick needs it: a DOM-writing system on main that keeps up.

- **N:** 1K ticks; usually 1–1.
- **Best:** 12,256 bytes per N at the copy bandwidth of one thread, the fastest it measured. One task moves its posted, done, payload and completion lines between cores, and the tail reads each row's 12-byte vec3.

### tail late snapshot 10K

A run writing what a late tail on a joined worker reads, 10,000 passing rows of a vec3 and a mat4: the copy of the tail's reads it makes first, as when main is busy when the next tick writes positions.

- **N:** 10K rows copied; usually 100–10K.
- **Best:** 172 bytes per N at the copy bandwidth of one thread, the fastest it measured. Each row's 12-byte vec3 and 64-byte mat4 are read and written, and its position, archetype, row and entity, 20 bytes, written.

### tail overlap

Ticks writing every row's place, which the last tick's tail on a joined worker still reads, then working 2 ms, while the tail works about 2.5 ms over 10,000 rows of a place and a pose: main's DOM work and the world's work after its writer that together outlast a frame or a fixed step, though each fits. The writer copies the rows the tail hasn't read, so the tick and the tail overlap.

- **N:** 100 ticks; usually 1–1.
- **Best:** 1,520,000 bytes per N at the copy bandwidth of one thread, the fastest it measured. The world copies each row's 12-byte vec3 and 64-byte mat4 the tail hasn't read, and the tail reads them, beyond the work each side does.

### tail overlap waiting

Ticks writing every row's place, which the last tick's tail on a joined worker still reads, then working 2 ms, while the tail works about 2.5 ms over 10,000 rows of a place and a pose: main's DOM work and the world's work after its writer that together outlast a frame or a fixed step, though each fits. The writer waits for the tail to finish instead, the alternative `tail overlap` is measured against.

- **N:** 100 ticks; usually 1–1.
- **Best:** 760,000 bytes per N at the copy bandwidth of one thread, the fastest it measured. The tail reads each row's 12-byte vec3 and 64-byte mat4, beyond the work each side does.

### transfer

Runs from a loader on a joined worker, each moving a 1 MB ArrayBuffer and a 1024 by 1024 ImageBitmap to the joined worker whose system takes them, which acknowledges each to the world: decoded textures or audio reaching the thread that uses them.

- **N:** 100 transfers; usually 1–100.
- **Best:** 256 bytes per N at the copy bandwidth of one thread, the fastest it measured. A transfer moves its values' handles in one message, the bytes staying where they are, and the run's slot and completion lines between cores.
